Predict AI — ML Prediction System

A modular machine learning system that handles both classification and regression behind one interface, with predictions served over a REST API. Reached 89% accuracy on datasets of up to 2,000 records.

The context

This was my first end-to-end machine learning system, built while finishing my B.Tech. Most ML examples in tutorials stop at "train a model and print the accuracy score". The gap I wanted to close was everything after that — the part that makes a model usable by someone who isn't the person who trained it.

The problem

Two related problems, both about the seam between a model and whoever uses it:

  • Task fragmentation. Classification and regression are usually taught as separate problems with separate codebases. A system that needs to do both ends up with duplicated training, serving, and validation logic.
  • The last mile. A trained model that isn't reachable from an application is a file sitting on a laptop. If other software can't call it, it isn't really a system.

The approach

One interface, two task types

The system is modular around a shared contract: data in, prediction out, regardless of whether the underlying task is classification or regression. Adding a task type means implementing one module rather than restructuring the project — which was the point of building it this way rather than as two scripts.

REST API for predictions

The model is served over a REST API rather than exposed as a library, because that's how the rest of a real system consumes it. Response time was a deliberate consideration: the API layer is thin, and the model is loaded once rather than per request.

Exposing a model over an API is a small amount of work that changes who can use it. It's also the step tutorials skip, and it's the step that turns a model into something you can put behind a product.

89% is on a classification task. It's a real number but a modest one, and I'd rather say that plainly than present it as a benchmark. The dataset size is small — at 2,000 records the ceiling is set as much by the data as by the model, and I was well aware of that while building it.

What I'd do differently

  • Report a proper baseline comparison. 89% is only interesting next to something else. Without a naive baseline in the same table, the number doesn't say much.
  • Set up the experiment before tuning. I tuned against the test set more than I should have. The reported figure is therefore optimistic, and I'd want a held-out split to state it honestly.
  • Add proper input validation at the API boundary. A model endpoint that accepts any shape will fail confusingly at inference time. Validating the request against what the model was trained on is part of serving it properly.
  • Version the models. A trained model is a dependency. I didn't track which model version backed a given prediction, which made old results hard to reproduce.
