ScraperAgent

An AI-powered candidate search and screening platform. You give it a job description; it searches the web for matching candidate profiles, merges the results, ranks them, and shows you a shortlist — instead of one long list of near-duplicates.

The context

This is my own project, built to solve a problem I kept running into while looking at how recruiting and sourcing actually works. The tools that claim to "find candidates from a job description" mostly do one thing: they run a single search and hand you whatever comes back. That result is noisy. The same person shows up four times with four different URLs, weak matches outrank strong ones, and a recruiter spends twenty minutes doing the deduplication by hand before they get to the part that matters — actually reading the profiles.

I wanted to build the thing that did that work. Not a model that hallucinates candidates — an actual pipeline that searches, merges, filters, and ranks what's genuinely out there.

The problem

Naive search has four failure modes, and each one needed a different fix:

  • Poor coverage. One search query finds what that query's ranking surfaces. A JD described as "Python developer with Django experience" and the same JD described as "backend engineer, web frameworks" return almost disjoint result sets.
  • Duplicates. The same person appears via their LinkedIn, a personal site, a conference bio, an aggregator, and a company team page. Without merging, the top of the list is the same three people repeated.
  • Irrelevant results. Job boards, aggregator articles, and "top 10 developers" listicles match the keywords without being a person at all.
  • Unstructured filters. "5+ years experience" is written as "5+ years", "5-8 yrs", "six years", "since 2019", and "3 years". "Delhi NCR", "New Delhi", "Delhi, India" and "NCR" all mean the same place. A literal string match filters out good candidates.

Constraints

Four things shaped the design, and they were constraints rather than preferences:

  • No scraped data centre. There is no database of candidates I'm allowed to query. Everything has to come from search results at request time.
  • Rate limits and cost. Search APIs bill per call. A user who runs the same search twice shouldn't cost twice.
  • It has to be a real product, not a script. A backend, a frontend that doesn't feel like a demo, automated tests, and something that runs where other people can use it.
  • Free-tier hosting. Render, which means the app sleeps and the cache has to survive that.

The approach

Multi-query search

Instead of one query per request, I derive several from the job description — the role title as written, synonym variants, and skill-derived phrasings — and run them across both Tavily and DuckDuckGo. The union of those result sets has noticeably better coverage than any single query, which is the first problem solved.

Deduplication

This turned out to be the highest-value part of the whole pipeline, and also the fiddliest. Identities are matched on more than URL: normalised names, plus contact handles where they're present in the result text. URL normalisation alone wasn't enough, because the same person genuinely does appear on several different domains.

Deduplication is what turns a long list into a shortlist. It's also the step most likely to be subtly wrong, so it's the part I tested hardest.

Extraction and filtering

Experience and location are parsed out of the result text rather than string-matched. Experience formats get normalised to a comparable form so a range, a "+" suffix, a spelled-out number, and a year range all reduce to something you can actually filter on. Locations resolve through an alias map, so the same city written several ways still matches the filter the user selected.

Relevance ranking

Surviving results are scored on how well they match the requested role, experience band, and location, and presented in ranked order. The point is that a recruiter should be able to read the first ten results and not need to look further.

Caching

Identical job descriptions get served from Redis instead of triggering a fresh set of paid search calls. Beyond the cost saving, it removes the multi-second wait on a repeat search — the difference between a tool people use twice and one they stop using.

Shipping it

FastAPI backend on Render, a responsive JavaScript frontend, and automated test coverage over the parsing, filtering, and dedup logic — the three places where a quiet regression would produce plausible-looking but wrong output.

Results

The honest way to report this is qualitatively, because I didn't run a controlled evaluation:

  • Coverage — noticeably better than a single query. Different query phrasings surface candidates the original search never returned.
  • Result quality — after deduplication, the top of the list is distinct people rather than the same profile five times.
  • Speed — repeat searches of the same JD are served from cache, which is the difference between an instant result and waiting on several search providers.
  • Cost — caching means the same JD is billed for once, not once per search.
  • Reliability — automated tests over parsing and dedup catch the failures that would otherwise show up as a confidently wrong shortlist.

What I don't have yet is a proper evaluation — a labelled set of JDs with known-good candidates, and measured precision@k. I know the ranking is better than nothing; I can't yet put a defensible number on by how much. That's the first thing I'd add.

What I'd do differently

  • Measure before optimising. I tuned the ranking heuristics before I had a way to score them. I was tuning blind, and the changes that felt right weren't necessarily the ones that helped.
  • Make the dedup decision visible. When two profiles get merged, the user should be able to see which sources were combined. Right now merging happens silently, which is convenient and slightly dishonest.
  • Start with one search provider. Running two providers in parallel from the beginning doubled the integration surface before I understood the shape of the problem. I'd have shipped one first, measured it, then added the second with evidence about what it was fixing.
  • Handle the free tier honestly. On Render the app sleeps when idle, so the first request after a quiet period is slow. I should have surfaced that in the UI instead of letting the user think the app had hung.
