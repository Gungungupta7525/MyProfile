Ranking web search results without drowning in duplicates

Multi-query search, deduplication, and relevance scoring — the approach behind ScraperAgent's candidate search pipeline.

  • ai
  • backend
  • search

I built ScraperAgent to search the web for candidate profiles from a job description. Writing that down taught me more than building it did, so here are the four problems and how I got past each one.

One query is one opinion about a role

The obvious implementation is: take the job description, search it, return results. The problem is that a search engine's ranking is a single opinion about what the role means, and it's an opinion shaped by whichever phrasing you happened to use.

A JD written as "Python developer with Django experience" and the same JD written as "backend engineer, modern web frameworks" return almost disjoint result sets. Neither is wrong. Together they're much closer to the real candidate pool.

So the pipeline derives several queries from one job description — the title as written, synonym variants, phrasings built from the required skills — and runs them across more than one provider. The union covers meaningfully more ground than any single query.

This is the cheapest improvement in the whole system. It's also the one most people skip, because a single query already returns results and it's easy to mistake "results" for "results".

Deduplication is the hard part

Expand the search and one consequence dominates everything else: the same person appears repeatedly. Different domains, different URLs, sometimes slightly different spellings of the same name. A naive implementation returns a top-ten list containing four people.

I tried matching on URL first, which is the obvious approach and the wrong one. The same person genuinely is on their LinkedIn, their own site, a conference speaker list, a company team page, and at least one aggregator. Deduplicating by URL collapses none of that.

Matching on normalised name plus any contact handle present in the result text does much better. It's also where the bugs live:

  • Two genuinely different people can share a common name.
  • One person's name is spelled differently across sources.
  • Unicode and punctuation variation that looks identical to a human.

Every fix for a false merge makes you slightly more likely to miss a true one. There's no threshold that solves it, only better signals and accepting that it'll be wrong sometimes.

Filters need parsing, not matching

This is the part that quietly ruins most search filters. Experience and location are written by humans, and humans do not write them in a canonical form.

"5+ years experience" arrives as all of these:

  • 5+ years
  • 5-8 yrs
  • six years
  • since 2019
  • 3 years (under-requirement, and you need to know that)

A literal string match throws most of these away, including people who are perfect. The fix is to parse into a comparable numeric form so that filters operate on numbers rather than text. Spelled-out numbers need mapping; a year range needs converting to a duration against a reference date.

Locations have the same problem in a different shape. These all mean the same place:

  • Delhi NCR · New Delhi · Delhi, India · NCR · Delhi

An alias map resolves them. It's unglamorous, it needs maintaining as new spellings appear, and it is the difference between a filter that works and one that silently discards good candidates.

Ranking what's left

After merging and filtering, surviving results get scored on fit against the requested role, experience band, and location.

Here's the part I'd flag for anyone building this: I tuned these heuristics before I had a way to score them. I was adjusting weights by intuition and looking at individual results, which feels productive and is close to worthless. I could tell that a change made one example look better. I could not tell that it made the system better.

The fix is unglamorous: assemble a small labelled set of job descriptions with known-good candidates, and measure precision@k against it. Then the tuning is against evidence instead of vibes. I should have built that first, before writing any ranking code.

Cache the expensive part

Search APIs bill per call and take real time. Recruiters re-run the same search constantly — a JD gets pasted, tweaked, and re-pasted. Caching on a normalised form of the job description means the same search is paid for once.

Beyond cost, it fixes the experience problem. A first search is a few seconds of waiting across several providers. The second is instant. That difference is most of what decides whether someone uses a tool twice or stops.

What I'd keep

  • Multi-query, always. Largest coverage win per line of code.
  • Parse filters, don't match strings. Silent data loss otherwise.
  • Cache aggressively. Cheaper and faster.
  • Evaluate before you tune. The one I keep skipping.

Deduplication is the one that rewards effort most and frustrates me most. It is also the difference between a search result and a shortlist.
