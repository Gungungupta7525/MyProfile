Driving SAP when there's no API to call

What SAP GUI automation is actually good for, where it falls short, and how to decide which one a process needs.

  • sap

A fair amount of my work at HCLTech is automating SAP processes, and a recurring question comes up early: is there an API for this? Sometimes yes. Often, honestly, no — and then the choice is between automating the GUI and telling the business the process can't be automated as designed.

Try the API first. Always.

This isn't controversial, but it's worth saying because the temptation runs the other way. If someone hands you a repetitive manual process, the instinct can be to start recording screens — it feels productive, and you can show something working in an afternoon.

Before recording anything, check what's already available: an OData or REST service exposed by the system, an existing BTP destination, a standard API on the transaction in question, or a BAPI function module for older releases. Any of these will be more stable, faster to run, and far easier to debug than a screen automation.

When GUI automation is the right answer

It genuinely is the right answer more often than people admit:

  • No interface exists at all. A legacy transaction with no service, no BAPI, and no OData. If the only way to get data out is the screen, the screen is the API.
  • Business logic lives in the transaction. A custom report or transaction that already computes the right answer. Reversing that logic outside SAP is re-implementing it badly.
  • Access is authorised at the transaction level. The user has a role that permits that transaction. An automation that calls the transaction respects the same authorisation model the user does.
  • It's a stopgap. Sometimes the right answer is an automation that works now while a proper interface gets built. The important part is being explicit that it's a stopgap.

The failure modes to plan for

A recorded screen automation is a promise that the screen stays the same. Everything below is a way that promise breaks:

  • Layout changes. A field moves and the selector misses. This is the one that will actually happen to you, and it's why selectors need to be resilient — based on labels and structure rather than fixed screen coordinates.
  • Pop-ups. Error dialogs, session timeouts, and "data has changed" warnings. The automation needs to read the screen and decide, not just follow a fixed script.
  • Timing. A slow transaction that times out, or a fast one the automation types into too fast. Fixed sleeps are a bug; you want to wait on actual state.
  • It fails silently. The most dangerous mode. A wrong value entered into a field is worse than a crash, because a crash is noticed.

A GUI automation that can quietly produce a wrong result is worse than no automation, because people stop checking.

Validation is the actual work

Recording a transaction is easy. The work is in the rest:

  • Confirm the data landed where it should, not just that the script finished.
  • Fail loudly on any unexpected state, instead of continuing.
  • Log enough to reconstruct what happened when it goes wrong.
  • Test it against the ugly cases — a missing field, an unexpected value, a session that expired mid-run.

On my current work, an automation extracts invoice data, writes it out, and triggers notifications. The extraction is the part everyone asks about. The validation is the part that determines whether anyone trusts it next month.

Where SAP BTP fits

SAP BTP and SAP Build Process Automation sit between the two worlds, which is why they're useful. Actions and Triggers give you an event-driven layer with proper retry and error handling around it, while the actual data movement can still be a call to an API, a BAPI, or a recorded transaction when nothing else is exposed.

What it doesn't remove is the need to decide which of the three you're using, and to be honest about it. An automation built on GUI recording presented as an API integration is a problem that surfaces later, usually during an incident.
